Non-premium players — sometimes called "cracked" players — use copies of Minecraft that are not tied to an official Mojang or Microsoft account. Because Mojang cannot verify their identity, anyone could join your server claiming any username. rLogin solves this by requiring non-premium players to register and protect their username with a password, ensuring that only the person who registered an account can use it.

## What Is a Non-Premium Player?

A non-premium (cracked) player is someone who launches Minecraft through an unofficial client or a launcher that is not authenticated with a Microsoft account. Their game sends no verifiable session token, so the server has no way to confirm who they are through Mojang. Without a plugin like rLogin, any player could join with any username — including the username of an existing player — and gain access to their progress.

## Registration Flow

The first time a non-premium player joins your server, rLogin blocks all movement and interaction until they create an account.

<Steps>
  <Step title="First join — registration prompt">
    The player connects and receives a message instructing them to register using the `/register` command.
  </Step>
  <Step title="Player registers">
    The player runs:
    ```bash
    /register <password> <confirmPassword>
    ```
    Both password fields must match. If they don't, rLogin asks the player to try again.
  </Step>
  <Step title="Password is hashed and stored">
    rLogin hashes the password with BCrypt before saving it to the database. The raw password is never written to disk or stored in any log.
  </Step>
  <Step title="Player gains access">
    After successful registration, the player is authenticated and all restrictions are lifted. They can move, chat, and interact normally.
  </Step>
</Steps>

<Info>
  Passwords are hashed with BCrypt before storage. Even if your database were ever compromised, attackers would not have access to your players' raw passwords.
</Info>

## Login Flow

On every subsequent join, rLogin recognises that the player already has an account and prompts them to log in.

<Steps>
  <Step title="Returning join — login prompt">
    The player connects and receives a message asking them to authenticate with `/login`.
  </Step>
  <Step title="Player logs in">
    The player runs:
    ```bash
    /login <password>
    ```
  </Step>
  <Step title="Authentication check">
    rLogin compares the provided password against the stored BCrypt hash. If it matches, the player is authenticated. If it doesn't, rLogin records the failed attempt.
  </Step>
  <Step title="Access granted or denied">
    On success, all restrictions are lifted. On too many failures, the player is kicked. If the player does not log in within the configured timeout window, they are also kicked automatically.
  </Step>
</Steps>

<Warning>
  Movement, chat, and all commands are blocked for unauthenticated players. Players who fail to log in within `login-timeout` seconds will be kicked from the server automatically.
</Warning>

## Password Requirements

You can configure minimum and maximum password lengths in rLogin's config file to enforce basic password strength:

```yaml
min-password-length: 6   # Default: 6 characters
max-password-length: 32  # Default: 32 characters
```

rLogin rejects registration attempts that fall outside these bounds and notifies the player with an appropriate message.

## Changing a Password

Players can update their own password at any time while logged in:

```bash
/changepassword <oldPassword> <newPassword>
```

rLogin verifies the old password before applying the change. If the old password is incorrect, the request is rejected.

## Admin Account Management

<Note>
  If a player loses access to their account or you need to reset their registration, you can unregister them as an administrator:

  ```bash
  /rlogin unregister <playerName>
  ```

  This removes their stored password and forces them to register again on their next join. Use this with care — it cannot be undone without a database backup.
</Note>
