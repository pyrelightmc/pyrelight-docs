rLogin supports session persistence, which allows authenticated players to be remembered for a configurable period after they disconnect. When a player reconnects within the session window from the same IP address, rLogin skips the login prompt entirely and restores their authenticated state automatically. This reduces repetitive logins for regular players while still giving you control over the security trade-off.

## How Sessions Work

After a non-premium player successfully authenticates, rLogin stores a session record tied to their username and IP address. If that player disconnects and reconnects before the session expires — and their IP address has not changed — rLogin recognises them and logs them in silently, without requiring a password.

Sessions are stored in memory and do not persist across server restarts by default. Once the session expires or the server restarts, the player must authenticate again normally.

## Configuring Session Timeout

Session persistence is controlled by the `session-timeout` option in rLogin's configuration file:

```yaml
session-timeout: 0  # 0 = disabled; any other value is the duration in seconds
```

The following table shows common configuration values and their effect:

| Value | Behavior |
|---|---|
| `0` | Sessions disabled — players must log in on every join |
| `300` | Session lasts 5 minutes after disconnect |
| `3600` | Session lasts 1 hour after disconnect |
| `86400` | Session lasts 24 hours after disconnect |

Set a value that reflects your server's audience and security requirements.

## Premium Players and Sessions

Session timeout settings do not apply to premium players. Premium players always authenticate automatically through Mojang's session API on every join, regardless of any session configuration. The `session-timeout` option only affects non-premium (cracked) players who use password-based authentication.

## Security Considerations

Sessions are bound to the player's IP address at the time of authentication. If a player's IP address changes between their disconnect and reconnect — for example, because they switched networks or their ISP reassigned their address — the session is invalid and they must log in again.

<Warning>
  On networks where multiple players share a single public IP address (such as NAT routers, school networks, or shared VPNs), one player's active session could theoretically allow another person on the same IP to bypass login. For public servers, keep `session-timeout` low or disabled.
</Warning>

## Recommendations

<Tip>
  For **public servers** with an open player base, set `session-timeout` to `0` or a very low value like `300` (5 minutes). This minimises the risk of session hijacking on shared or dynamic IP environments.
</Tip>

<Tip>
  For **private or trusted servers** — such as a server for friends or a whitelisted community — a longer timeout like `3600` (1 hour) or higher significantly reduces friction for players who reconnect frequently without meaningfully increasing risk.
</Tip>
